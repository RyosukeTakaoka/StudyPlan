# 設計書：手書きボード受け口アプリ（仮）

作成日：2026-10-21
状態：初版（実際に使ってみて改善する前提のたたき台）

---

## 1. 目的（このアプリは何のためにあるか）

**同じ場所に手書きを書き続ける人のために、写真を「見られる・持ち出せる・実績が残る」記録に変える。**

- 書くのは、これまで通り紙やホワイトボード。アプリの中では書かせない。
- 写真アプリは「1枚ずつ時間順にしまう箱」。このアプリは「同じ場所の毎日の変化を扱う道具」。
- 比べる・解釈する・コーチングするのはAIの役割。アプリは「見る・持ち出す・実績を記録する」だけに集中する。
- カレンダー登録などは作らず、他のアプリやAIとの連携に任せる。

### 想定ユーザー
1. 毎日ホワイトボードや紙に予定を書く人（最初のターゲット。開発者本人）
2. 手書きノートを毎日同じ形式で書く人（勉強ノート、日記、手帳など）

### 競合との違い
| 競合 | その特徴 | このアプリの立ち位置 |
|---|---|---|
| iPhoneの写真アプリ | 1枚ずつ時間順に並べる | 「同じ場所」を時系列で束ね、カード単位で扱う |
| Appleメモ | 何でも入る箱 | ボードという単位と、完了の状態を持つ |
| Adobe Scan | 書類1枚を取り込む | 毎日続ける人向けに、撮影も見返しも速くする |
| AI内蔵のノートアプリ | アプリ側でAIを持つ | AIは外部のものを使う。運営側の費用はほぼかからない |

## 2. 設計の考え方（根拠のある原則）

| 原則 | 理由（調査で分かったこと） |
|---|---|
| 筆跡を主役にし、文字起こしは裏方にする | 紙派が欲しいのは「紙をやめること」ではなく、紙のまま検索・持ち出し・記録の便利さだけ。文字認識の精度が不安定な手書きで、テキスト表示を主役にすると不満が出やすい |
| 「見返し」を中心に据える | メモは書くことより、保存して見返すほうが効果がはっきりしている。写真を撮って終わりだと、かえって記憶が弱まるという研究もある |
| 実績を記録する | 進み具合を記録すると目標を達成しやすい（138研究のメタ分析）。AIはあなたが実際にやったかを知らないので、記録できるのはアプリだけ |
| 整理を求めない | 整理の手間は、書くことの気軽さを壊す。フォルダやタグは作らない |
| 学習効果を売りにしない | 手書きが学習に効くかは研究で結論が割れている。「手書きの習慣を支える」と位置づける |

## 3. 機能一覧

### 3-1. 決定済みの核となる2機能
| 機能 | 内容 |
|---|---|
| **A. 筆跡カード** | 写真を行やブロックごとに切り出し、自分の筆跡のままカードとして並べる。裏に文字起こしを持ち、ワンタップで切り替えられる |
| **B. 今→次の表示** | ロック画面・ホーム画面のウィジェットなどに、「今のブロック」と「次のブロック」を表示する。ホワイトボードの前にいなくても見られる |

### 3-2. 追加する機能（優先順）
| 優先 | 機能 | 役割 | 版 |
|---|---|---|---|
| 1 | **定点撮影モード** | 前回の写真を半透明で重ね、毎日同じ構図で撮る。台形の歪みを補正し、ボードの枠を自動で検出する | v0.1 |
| 2 | **実績チェックと持ち越し** | カードごとに「完了／未完了／持ち越し／スキップ」をワンタップで記録。持ち越した回数も数える | v0.1 |
| 3 | **AI連携の口** | 計画と実績を、AIが読める形で外に出す。最初はApp Intentsと書き出し、将来はMCP | v0.2〜v0.3 |
| 4 | **並べて比較するビュー** | 日付をスワイプして、昨日・先週の同じボードを並べる。差分の解釈はしない（見せるだけ） | v0.2 |
| 5 | **時間ログ** | 開始・終了をワンタップで記録し、予定と実績の差が残る | v0.2 |
| 6 | **筆跡のまま検索** | 端末内で文字認識し、ヒットした場所を筆跡画像上でハイライトする | v0.2 |
| 7 | **見返しのきっかけ通知** | 「先週の今日」などを週1回だけ静かに表示。開いたら、答えを見る前に思い出す流れにする | v0.3 |
| 8 | **検索できるPDFでの書き出し** | 日・週・月のアーカイブを書き出し、他のアプリに持ち出せるようにする | v0.2 |
| 9 | **端末内処理とプライバシー設計** | 写真と文字認識は端末内で完結。AIに渡すのは、ユーザーが選んだときだけ | 常時 |
| 10 | **手書き記号による分類**（□・★・→など） | 記号からブロックの種類を自動分類する | 後回し（検証が必要） |

### 3-3. あえて作らないもの
| 作らないもの | 理由 |
|---|---|
| アプリ内での手書き入力 | 受け口に徹する方針。Goodnotesなどと正面衝突する |
| AIによる要約・評価・コーチング | AI側に任せる分担 |
| カレンダー機能・予定登録 | 連携先に任せる |
| フォルダ・タグの細かい整理 | 整理の手間が気軽さを壊す |
| 共同編集・SNS共有 | 1人用の道具のため、当面は不要 |

## 4. 1日の流れ（ユーザー体験）

1. 紙やホワイトボードに書く
2. アプリを開く（または、ロック画面やアクションボタンから起動）
3. 前回の写真が半透明で重なった画面で、構図を合わせて撮る
4. 自動で枠が検出され、カードに切り出される
5. 確認画面で、カードの区切りと時刻を直す（3タップ以内が目標）
6. 日中はウィジェットで「今→次」を見る
7. ブロックが終わるたびに、ワンタップで実績を記録する
8. 必要なときに、AIがアプリのデータを読んで比較・コーチングする

## 5. データ設計

### モデル
| モデル | 主な中身 |
|---|---|
| `Board` | 名前（例：自室ホワイトボード）、種類（ホワイトボード／ノート／紙）、前回の基準写真 |
| `Snapshot` | 所属する `Board`、撮影日時、対象日、元写真、補正後の写真、文字認識の全文 |
| `Card` | 所属する `Snapshot`、切り出し範囲、筆跡画像、文字起こし、開始・終了時刻、状態、持ち越し回数、持ち越し元の `Card` |
| `TimeLog` | 所属する `Card`、実際の開始・終了 |
| `Settings` | 通知、書き出し形式、AI連携の許可 |

### カードの状態
`予定` → `完了` / `未完了` / `持ち越し` / `スキップ`

### AIに渡す形（JSONの例）
```json
{
  "board": "自室ホワイトボード",
  "date": "2026-10-21",
  "cards": [
    {
      "id": "c1",
      "text": "鑑定理論",
      "handwriting_image": "cards/2026-10-21/c1.png",
      "start": "07:00",
      "end": "08:00",
      "status": "done",
      "actual_start": "07:05",
      "actual_end": "08:10",
      "carried_over_count": 0
    }
  ]
}
```

## 6. 技術の選択

| 領域 | 選択 | 説明・注意点 |
|---|---|---|
| UI | SwiftUI。iPadは `NavigationSplitView` | iPadは2画面、iPhoneは1画面に自動で切り替わる部品 |
| 保存 | SwiftData | iOS 17以降で使える、Appleのデータ保存の仕組み |
| 撮影 | AVFoundation | 前回の写真を半透明で重ねる画面は自作する |
| 枠の検出・補正 | Vision（矩形検出）＋Core Image（台形補正） | ホワイトボードの反射でうまく検出できない場合の手動調整も用意する |
| 文字認識 | Vision（端末内） | 日本語の手書きの精度は未検証。自分の写真で測る |
| ウィジェット | WidgetKit | 時刻ごとの表示予定をあらかじめ登録でき、サーバーは不要。更新回数には上限がある |
| ロック画面の進行表示 | Live Activities（ActivityKit） | 開始の条件や、連続表示できる時間に上限があるため、v0.1ではウィジェットを主役にして、効果を確かめてから追加する |
| AI連携 | App Intents →（将来）MCPサーバー | MCPは外のAIが届くよう、クラウドへの保存・ログイン・権限管理が必要になる。v0.3以降 |
| 筆跡画像の共有 | App Group（アプリとウィジェットでデータを共有する仕組み） | ウィジェットが画像を表示するために使う |
| 書き出し | PDFKit | 検索できるPDFを作る |

### 最大の技術的リスク：カードの切り出し
「行やブロックごとの切り出し」と「時刻の割り当て」は、一番難しい部分。

- **v0.1の方針**：文字認識の位置情報から区切りを提案し、ユーザーが確認画面で直す。完全自動は目指さない。
- **別ルート**：ユーザーのAIが写真を読み、結果をApp Intents経由でアプリに書き込む。
- 同じボードなら、レイアウトの癖を再利用できる可能性がある（要検証）。

## 7. UI方針（詳細は [UI_GUIDELINES.md](UI_GUIDELINES.md)）

- **主役は筆跡。** 文字起こしは裏方
- **拡大・横スクロールをさせない。** キャンバス型にしない
- **iPhone**：縦に並んだカードと、「今→次」を大きく見せる画面
- **iPad**：左に元の写真、右にカードの2画面
- **確認画面が最重要**：読み取りに自信のない項目を目立たせ、3タップ以内で直せる
- **静かなUI**：通知を最小限にして、見返しのきっかけも週1回程度にする

## 10. リスクと注意点

- **手書きの文字認識の精度**：日本語の手書きでは精度が不安定。筆跡を主役にして、認識結果は補助にする設計で和らげる。
- **定点撮影の需要は仮説**：「同じ場所を定期的に撮りたい」という要望そのものは、調査では見つかっていない。
- **似たアプリの存在**：手書き計画の取り込みや時間割表示をうたうアプリはすでにある。差は「筆跡のままの表示」と「実績をAIに渡す口」に置く。
- **ウィジェットとLive Activitiesの制限**：更新頻度や表示時間に上限がある。早めに試作して確かめる。
- **MCPの重さ**：外のAIとつなぐにはクラウドとログインが必要で、個人開発の負担が大きい。最後に回す。
- **試験との両立**：開発に時間を使いすぎない。週5時間の上限と、2027年3月以降の凍結を守る。
- **写真のプライバシー**：ホワイトボードには生活リズムが写る。端末内保存を基本にして、AIに渡すのはユーザーが選んだときだけにする。

## 追加：クラウド連携（MCPサーバー）とAPI設計

※ v0.1ではサーバーを作らない。この章はv0.3向け。ただし、v0.1のデータモデルだけは、後で同期しやすい形にしておく。
作り方の手順は [SERVER.md](SERVER.md)。

### 0. v0.1から今すぐ変えること（アプリ側）
- 全モデル（Board / Snapshot / Card / TimeLog）に次を持たせる
  - id: UUID（端末で生成）
  - updatedAt: Date
  - deletedAt: Date?（削除は消さずに印を付ける「論理削除」）
- アプリ内のJSON表現 DayPlanDTO を1つ決める。App Intents（v0.2）とMCP（v0.3）で同じものを使い回す
- アプリはサーバーなしで完全に動く。クラウド同期は、設定で明示的にONにしたときだけ動く（初期値OFF）

### 1. サーバー構成（決定）
- Cloudflare Workers + D1（TypeScript）
- 画像はサーバーに送らない（v0.3の範囲）。送る必要が出たら、R2（Cloudflareのファイル保存）を検討する
- 他の候補（AWS、Supabase）は使わない。理由は、設定の部品が多いこと、無料プランが1週間アクセスがないと止まることの2点

### 2. 認証
- MCP側：OAuth。Cloudflare公式テンプレート remote-mcp-github-oauth（または google-oauth）を出発点にする。許可するアカウントは自分1つだけに制限する（環境変数の許可リストで管理）。認証なし（authless）のまま、実データを載せて公開しない
- アプリ側：端末ごとのAPIトークンを使う。トークンはKeychainに保存し、サーバー側ではwrangler secretで管理する
- Claudeのカスタムコネクタは、リモートのMCPサーバーを指す。SSEとStreamable HTTPの両方に対応しているので、Streamable HTTP（/mcp）を優先する

### 3. データ（D1テーブル）
- 共通の列：id, updated_at, deleted_at
- boards：name, kind
- snapshots：board_id, target_date（YYYY-MM-DD）, captured_at
- cards：snapshot_id, date, text, start（HH:mm）, end, category, status, carried_over_count, carried_from_card_id, has_handwriting_image
- time_logs：card_id, actual_start, actual_end
- status は planned / done / not_done / carried / skipped の5つ
- タイムゾーンは Asia/Tokyo 固定。インデックスは cards(date) と cards(status)

### 4. 同期API（アプリ ↔ サーバー）
- バージョン番号を付ける（/v1）
- POST /v1/sync/push：変更分をまとめて送る（追加・更新・論理削除）。同じ内容を2回送っても結果が変わらない作りにする（冪等）
- GET /v1/sync/pull?since=：サーバー側の変更を取得する（フェーズBから）
- 競合したときは、updated_at が新しい方を採用する
- DELETE /v1/data：自分の全データを削除する

### 5. MCPツール（Claudeが呼ぶ道具）
フェーズA：読み取り専用（readOnlyHint を付ける）
- get_day_plan(date)：指定日のカード一覧（時刻・文字起こし・状態・持ち越し回数）
- list_days(from, to)：日ごとのカード数と状態別の件数だけを返す
- get_review_context(date, days_back)：前日までの計画と実績をまとめて返す（days_back は最大7）
- list_carried_over_cards(since)：持ち越しになっているカード一覧

フェーズB：書き込み（アプリが pull で受け取る）
- update_card_status(card_id, status)
- log_actual_time(card_id, actual_start, actual_end)

作らないもの
- AIが写真を読んでカードを新規作成するツール（双方向の同期が安定してから検討）
- 要約・評価・助言のツール
- 削除ツール

共通ルール
- 返すのはJSONのみ。解釈・評価・助言は含めない（それはAIの役割）
- 1回の返却は小さくする（日付範囲に上限を設ける）
- 各ツールのdescriptionに、いつ使うか、引数の形式、日付はAsia/Tokyoであることを書く
- 入力は検証する（zodなど）。エラー文は分かりやすくする
- ログにカードの文章を出力しない

返却JSONの例（DayPlanDTO）
```json
{ "date": "2026-10-21", "cards": [ { "id": "...", "text": "鑑定理論", "start": "07:00", "end": "08:00", "status": "done", "actual_start": "07:05", "actual_end": "08:10", "carried_over_count": 0, "has_handwriting_image": true } ] }
```

## 実装で決めたこと（2026-10-21）

| 項目 | 決めたこと | 理由 |
|---|---|---|
| クラウドの分担 | 端末どうしの同期は **CloudKit**（SwiftData の標準機能、`cloudkit/schema.ckdb`）。Claude 向けの MCP と同期 API は **Cloudflare Workers + D1** | ご指示（2通）の両方を生かす。どちらも設定でオンにしたときだけ動く |
| 公開ページの URL | プライバシーポリシーとサポートは **GitHub Pages**（`site/`） | サーバーは GitHub Pages に置けないため、サーバーの URL は workers.dev を使う |
| Xcode プロジェクト | `StudyPlan.xcodeproj` をリポジトリに入れ、`git pull` してそのまま開ける形（フォルダ同期） | XcodeGen を使わない方針のため |
| `Settings` モデル | SwiftData のモデルにせず、`UserDefaults`（`@AppStorage`）に保存 | 端末ごとの設定で、同期の対象ではないため |
| 持ち越し元 | `Card.carriedFromCardID`（UUID）で持つ。前7日の「持ち越し」と同じタイトルのカードを撮影時につなぎ、回数を引き継ぐ | CloudKit とサーバーの列（carried_from_card_id）にそのまま対応させるため |
| DayPlanDTO | 例の項目に `category` を足した | D1 の cards.category と同じ値で、AI にも役立つため |
| D1 | 各表に `synced_at`（サーバーが受け取った時刻）を足した | `pull` の目印。端末の時計のずれや件数の多さで取りこぼさないため（`has_more` で続きを返す） |
